## Part 1 — CONTEXT BLOCK (M6 slice)

```
PROJECT
AI Governance Gateway. A Chrome extension plus a FastAPI policy plane that
inspects prompts and file attachments before they reach ChatGPT, Gemini or
Copilot, and returns one of four verdicts: allow | redact | hold | deny.
Every event lands in an auditable log. This module is the employer's view of
that log, and the place a held prompt gets approved or denied.

REPO LAYOUT (do not deviate)
  dashboard/                      M6  React + Vite + TypeScript    <- YOU
    index.html
    vite.config.ts
    tailwind.config.js
    .env.example                      VITE_API_BASE, VITE_API_KEY, VITE_USE_MSW
    src/main.tsx                      entry, TanStack Query provider
    src/App.tsx                       router + hardcoded admin login
    src/index.css                     Tailwind; 16px minimum body text
    src/api/types.ts                  wire types, mirror of the contracts below
    src/api/client.ts                 EVERY network call, one module
    src/api/queries.ts                TanStack Query hooks, refetchInterval 3s
    src/screens/AuditLog.tsx
    src/screens/ApprovalQueue.tsx
    src/screens/Overview.tsx
    src/screens/PolicyAndTools.tsx
    src/components/VerdictBadge.tsx
    src/components/DataClassPills.tsx
    src/components/EmptyState.tsx
    src/mocks/handlers.ts             MSW, opt-in, default OFF
    src/mocks/browser.ts
    README.md
  backend/                        M0+M1  BUILT, SEEDED, TESTED.
                                  A black box behind IF-7 and IF-10.
  extension/                      M4  BUILT. You never talk to it.

FROZEN CONTRACTS
Never change these. Other modules are written against them in parallel by
people who cannot see your code. You consume IF-7 and IF-10 and nothing else.
You never read the database. You never talk to the extension.

AUTH
  Every request carries  X-Api-Key: <VITE_API_KEY>.
  Wrong or missing key -> 403. CORS already allows http://localhost:5173.

SHARED ENUMS -- the spine of the whole system. They do not change.
  decision : "allow" | "redact" | "hold" | "deny"     the verdict the engine reached
  status   : "auto" | "pending" | "approved" | "denied"   the human review outcome
  The two are orthogonal and both are shown. set_decision NEVER touches
  decision: the verdict is a historical fact, the review outcome is status.
  An approved row still reads decision="hold", status="approved". That is
  correct and must not be "fixed" in the UI.

AuditRecord -- the row shape everywhere the log is returned
  {
    log_id: string
    user_id: string
    ts: string                      // ISO 8601, UTC
    target_host: string
    prompt_text: string             // FULL prompt. When decision=="redact"
                                    // this is ALREADY the redacted text; the
                                    // original lives only in the encrypted
                                    // vault. See the note in the task.
    filename: string | null
    data_classes: string[]          // e.g. ["MYKAD","PERSON"]
    decision: Decision
    reason: string                  // one human-readable sentence, from M3
    status: LogStatus
    reviewer: string | null
    reviewed_at: string | null      // ISO 8601
    remark: string | null
    map_id: string | null           // set when decision=="redact"
    user_department: string | null      // who the person IS. From the users table.
    content_department: string | null   // what the prompt is ABOUT. From M8.
    department_confidence: number       // 0.0 - 1.0
  }

IF-7  Dashboard -> API

  GET /v1/logs
    query: limit (1-200, default 20), offset (>=0, default 0),
           status?, decision?, cross_department_only? (bool, default false)
    -> { items: AuditRecord[], total: number, limit: number, offset: number }
    Ordering: newest first (ts desc). Guaranteed by the server.
    `total` is the count matching ALL filters, before limit/offset. Page from it.

  POST /v1/logs/{log_id}/decision
    body: { approve: boolean, remark: string }     // remark is REQUIRED
    -> AuditRecord
    404 on unknown log_id.

  GET /v1/stats
    -> {
         by_decision: Record<string, number>
         by_day: [string, string, number][]        // [iso_date, decision, count]
         top_data_classes: [string, number][]      // [data_class, count]
         top_users: [string, number][]             // [user_id, count]
       }
    Tuples arrive as JSON ARRAYS, not objects. Read the note in the task.
    by_day: date asc, then decision asc.
    top_data_classes / top_users: count desc, key asc as tie-break, max 10.
    top_users counts RISK events only (decision != "allow"). Label the column
    exactly that: fifty clean prompts must not make somebody the riskiest
    person in the company.

IF-10  Dashboard -> API

  GET /v1/rules
    -> { data_class: string, ai_tool_tier: string, user_role: string,
         purpose: string, decision: string }[]

  GET /v1/tools
    -> { host: string, tier: string, status: string,
         approved_by: string | null, approved_at: string | null,
         first_seen: string, usage_count: number }[]
    tier   : "PUBLIC_AI" | "ENTERPRISE_AI" | "INTERNAL_AI"
    status : "approved" | "unapproved" | "blocked"
    Ordering: unapproved and blocked FIRST, then host asc. Guaranteed by the
    server. Do not re-sort.

  POST /v1/tools/{host}/decision
    body: { status: "approved" | "blocked", remark: string }
    -> the updated tool. 404 on unknown host.

  GET /v1/health
    -> { status: "ok", mocked: string[] }     // e.g. ["M2","M3","M5","M7","M8"]
    Which backend modules are still mocks. Surface it; see the task.

GROUND RULES
1. The contracts above are law. If your module seems to need a change, stop
   and say so. Do not change it locally.
2. Build ONLY M6. The backend is somebody's finished work; the extension is
   somebody's finished work. You do not open either.
3. The stack is fixed: React, Vite, TypeScript, Tailwind, TanStack Query,
   Recharts, MSW, react-router. Do not add a component library, a table
   library, a second chart library, or a state manager. TanStack Query IS the
   state manager; server data has one home.
4. Poll. Every 3 seconds, via TanStack Query refetchInterval. No WebSockets,
   no SSE, no socket.io.
5. Ship a way to prove it works without the rest of the system running.
6. Policy is data, not code. Rules and tool tiers are rows an admin edits at
   runtime. Never hardcode a rule, a hostname-to-tier mapping, or a
   host-to-department mapping anywhere in this dashboard.
```

## Part 2 — M6 TASK

```
TASK: build M6, the employer dashboard. Four screens over IF-7 and IF-10.

WHY THIS ONE LOOKS FINISHED. Design is 15% of the preliminary score and the
extension has almost no UI surface -- a banner and a popup. Every one of those
marks lives here. This is also the only screen a judge sees for more than five
seconds. Make it look finished: real empty states, real loading states, no
placeholder text, no lorem, nothing that renders "undefined".

THE BACKEND IS BUILT AND SEEDED. Do not stub it, mock it in place of it, or
"improve" it.
    cd backend && REPO_BACKEND=memory uvicorn app.main:app --reload
No Docker needed. It comes up seeded with 4 users, 15 rules, 3 AI tools and 30
audit rows spread over 7 days -- deliberately, so your charts have something in
them from the first render and the cross-department filter has something to
find. Point at it: VITE_API_BASE=http://localhost:8000, VITE_API_KEY from
backend/.env.

MSW IS THE FALLBACK, NOT THE DEFAULT.                             [CHANGED]
The plan doc specced MSW-first because the backend did not exist yet. It does
now. So: VITE_USE_MSW=false by default; MSW starts only when it is explicitly
true. Same shape as M4's mock.ts -- an offline path you opt into, never one you
fall into. Still BUILD the mock handlers for /v1/logs, /v1/stats, /v1/rules and
/v1/tools and keep them honest: they are what lets you work on a train, and
what saves the demo if the hosted API is asleep. A mock you discover you were
running is worse than no mock at all.

-------------------------------------------------------------------
SCREEN 1 -- Audit log.  The main event.

Table over GET /v1/logs: user, timestamp, target host, prompt excerpt,
filename, data classes as pills, verdict as a coloured badge, status.

  - Colour: allow green, redact amber, hold amber, deny red. PAIR EVERY COLOUR
    WITH A TEXT LABEL. Never colour alone. Two verdicts share amber, so colour
    alone is not merely an accessibility failure here -- it is ambiguous to
    everyone. Judges include people who cannot distinguish them.
  - Filter by verdict and by status. Paginate off `total`. Poll every 3s.
  - Row expands to show the full reason string from M3 VERBATIM. Do not
    truncate it, do not rewrite it, do not prettify it. That sentence is the
    system explaining itself, and it is the answer to "why was I blocked".
  - Two department columns: "user" (who the person is) and "content" (what the
    prompt is about, from M8).

THE CROSS-DEPARTMENT VIEW. This is the single most interesting view in the
whole dashboard: an engineer working on payroll data is a governance signal no
single-column view surfaces. Get it exactly right.

  - Badge the row when, and only when:
        content_department != null && user_department != null
        && content_department != user_department
        && department_confidence > 0.6
    Strictly greater than 0.6. This predicate is IDENTICAL to the server's
    cross_department_only filter, deliberately. Write it ONCE, in one exported
    function, and use it for the badge. If the badge and the filter drift, the
    toggle shows rows that are not badged and the screen quietly stops making
    sense. Put a comment on that function saying it mirrors the server.
  - Badge colour is paired with a text label. Never colour alone.
  - At or below 0.6 confidence: render the content column MUTED, and do not
    badge. Do not hide the number behind a badge you cannot justify. Show the
    confidence value.
  - content_department == null renders as an em dash. NOT "unknown", not
    "none", not an empty cell. M8 is still mocked (check GET /v1/health): its
    classify() returns null honestly, so every row the extension creates right
    now has a null content department. The 30 seeded rows DO carry departments,
    including planted mismatches -- that is what you develop against, and that
    is what the demo shows.
  - A "cross-department only" filter toggle. It sends
    cross_department_only=true to the server. It does NOT filter the array you
    already have: filtering the loaded page would show 1 of 3 mismatches and
    look perfectly correct doing it. It composes with the verdict and status
    filters, and `total` updates -- so the pagination follows the filter.

ON prompt_text: when decision=="redact" the log already holds the REDACTED
text. The original is in the encrypted vault, admin-only, and retrieving it is
itself audited. That is deliberate: an audit log of every prompt in the company
is the most sensitive table we own, and the redaction is what makes storing it
defensible. Do NOT add a "reveal original" button to this screen. Do not fetch
/v1/detokenise. If it looks like data is missing, it is not -- that is the
feature.

-------------------------------------------------------------------
SCREEN 2 -- Approval queue.  The loop that makes it a governance tool.

  - GET /v1/logs?status=pending only. Server-side, not a client filter.
  - Approve and Deny buttons -> POST /v1/logs/{id}/decision with an optional
    remark. The API requires the field: send remark: "" when it is blank.
    Do not invent a placeholder remark; an empty remark is a real answer.
  - Optimistic update, rollback on error.
  - The 3s poll and the optimistic write will race. In onMutate, cancel
    in-flight queries for that key before you write the cache, or a poll that
    was already on the wire lands afterwards and silently reverts the row --
    which looks exactly like the button did nothing.
  - The extension is polling IF-3 and unblocks the employee within 3s of your
    write. Say so in the UI, in one line, near the buttons. That sentence is
    the whole product: somebody is sitting in front of a frozen composer.

-------------------------------------------------------------------
SCREEN 3 -- Overview.  Recharts over GET /v1/stats.

  - Verdicts per day: stacked bar. Top data classes: bar. Top users by risk
    events: bar (label it exactly that -- see the contract).

  THE PIVOT IS THE BUG IN THIS SCREEN. by_day arrives as a flat list of
  [date, decision, count] arrays -- Python tuples over JSON, so ARRAYS, not
  objects. Recharts wants one object per day: {date, allow, redact, hold, deny}.
  A day with no rows for a given decision is ABSENT from the list, not zero. If
  you spread the list into objects without filling every missing key with 0,
  the stack renders with holes and looks fine -- a chart that is wrong and
  confident is worse than one that is empty. Fill all four keys, every day.
  Write a unit test for the pivot with a sparse day in it. This is the one
  place in M6 that fails silently.

  - Colour the stack with the same verdict colours as screen 1. One palette,
    one meaning, defined once and imported.

-------------------------------------------------------------------
SCREEN 4 -- Policy and tools.  The proof that policy is not hardcoded.

  - Rules table over GET /v1/rules: data class, tier, role, purpose, verdict.
    Read-only is fine for the MVP; an edit form is a stretch goal, not scope.
    Showing the rules AT ALL is the point: it is the visible proof that policy
    is configuration an organisation owns, not something we hardcoded. Say that
    on the screen, in one line, in plain English. Do not make the judge infer it.
  - Tools table over GET /v1/tools: host, tier, status, first seen, usage count.
    Unapproved rows get a badge -- colour plus label -- and they ALREADY sort to
    the top; the server guarantees the order. Do not re-sort the array and undo
    it.
  - first_seen is when the host was first ever seen and it never moves. A host
    that shows up here that nobody configured is shadow AI, discovered on first
    use, and first_seen is when it happened. Format it as a real date, not a
    relative "2 days ago" -- this column is evidence.
  - Approve and Block buttons per tool -> POST /v1/tools/{host}/decision with
    {status, remark}. Approve sends "approved", Block sends "blocked". This is
    example use case 2 from the case study brief -- "implement approval
    workflow for AI tool usage" -- and it is about twenty lines on top of the
    approval queue from screen 2. Same optimistic pattern, same race, same fix.

-------------------------------------------------------------------
SHELL

  - Auth: hardcode an admin login for the demo. Do NOT build real auth. It is
    cosmetic: the backend records DASHBOARD_ADMIN as the reviewer regardless of
    what the form says. One line of comment in App.tsx saying exactly that, so
    nobody later "fixes" the form into a false claim about who approved what.
  - Surface GET /v1/health somewhere small and permanent -- a footer chip.
    "Live" when mocked is empty; "Mocked: M2, M3, M5, M7, M8" when it is not.
    A judge asking "is any of this real?" should be answered by the app, not by
    a person. It also stops YOU from demoing against mock detection by accident.

DESIGN

  - Judges see this on a projector. 16px minimum body text. Check contrast on
    every badge; the amber pair is where it will fail.
  - Colour never carries meaning alone, anywhere.
  - Empty state and loading state for EVERY screen and every table. Not a
    spinner over the whole page: skeleton rows, so the layout does not jump
    every 3 seconds when the poll lands. A dashboard that flickers on a
    projector looks broken even when it is not.
  - No dead controls. If it cannot be clicked, it is not on the screen. An edit
    button that does nothing costs more marks than a missing feature.

DELIVER
  - A running dev server against the live backend, and the same app running
    with VITE_USE_MSW=true and the backend stopped.
  - .env.example with all three vars and a one-line comment each.
  - Unit test for the by_day pivot, including a sparse day.
  - Unit test for the cross-department predicate, including exactly 0.6.
  - README.md: how to run it, what VITE_USE_MSW does and when to reach for it,
    and the one paragraph naming which screens are read-only in the MVP.
```

## Notes for you, not for the paste

- **The seeded mismatches are load-bearing.** `seed.py` plants them in
  `_MISMATCH` at 0.62–0.91 confidence, on purpose, with a comment explaining
  why not more: seed 60% mismatch and the filter finds nothing useful. Screen 1's
  headline view demos off seed data, not off live extension traffic — live rows
  carry `content_department: null` until M8 lands. Worth knowing before you
  record.
- **`usage_count` is still the open item** in `README_M0.md`. M1 derives it by
  paging the audit log and counting in Python — free at 30 rows, not free at
  30,000. It is honest and it is documented; leave it. If a judge asks, that
  answer is better than a hidden N+1.
- **Two screens, one optimistic-write race.** Screens 2 and 4 have the identical
  poll-vs-mutate problem. If Codex solves it twice, differently, pull it into one
  hook before the session ends.
